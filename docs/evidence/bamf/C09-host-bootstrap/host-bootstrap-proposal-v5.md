# C09 host-bootstrap remediation proposal v5

Status: PROPOSED v5 / issue #1030 / implementation frozen pending fresh formal review.

Supersedes for design purposes only: failed v4 at
`899eb017d9842c4fb2e5a5e4f5ebcb517d5fce2a`. The v4 files remain immutable failed
review evidence and MUST NOT be rewritten or treated as approved design.

Reviewed integration base: `97a018ed7e9697fe284abd9fa8197cd7f4194b45`.

## 1. Why v5 exists

The fresh pinned-EGM review of v4 found no Blockers but found material Majors in all
three review lenses. v5 resolves those findings before production implementation:

1. remove the overbroad external `RIGHTS rights:` authority;
2. make the C13 capability-support namespace an executable Factory/source-binding
   invariant rather than a bootstrap-time census assertion;
3. require durable directory metadata before activation renames;
4. make recoverable private-key custody a mechanical precondition of registry
   activation rather than an operations-doc promise;
5. make the public bootstrap package self-identifying and digest-authenticated;
6. provide complete A12 and C07 typed canary context, not signatures without the
   context required by the real validators;
7. prove the C06 signer through the actual runtime UID rather than a root-only readback;
8. freeze exact CLI grammar, artifact schemas, paths, and mutation surfaces;
9. pin Darwin signer ACL semantics to `ACL_READ_DATA` for exactly one runtime UID;
10. preserve registry rename as the final activation event only after every pending
    artifact and containing-directory state is durable.

No runtime caller may select a registry path, signer path, owner set, scope set, or
bootstrap manifest. The existing #950 fixed host trust boundary remains fail-closed.

## 2. Frozen authority census

The newborn `HOST_SYSTEM_V1` registry contains exactly four public authority identities.
The machine-readable contract is `authority-manifest-v2.json`.
Machine-facing bootstrap constants, CLI arguments, canonical JSON rules, fixed host paths,
new schema field sets, and the exact A12 canary pin are frozen in `bootstrap-contract-v1.json`.

### 2.1 C06 host priority signer

Owner: `owner:c06`.

Private key: generated by the operator administration flow before Studio activation,
durably duplicated across independent storage, then imported by the root installer into the
fixed signer file. The Studio receives only one protected transfer copy. Runtime access is
read-only and limited to the configured Bilqis runtime UID.

Scopes:

- `POLICY salience-policy:`
- `SOURCE salience-fact:`
- `ARTIFACT salience-option:`
- `ARTIFACT salience-event:`

No additional C06 namespace is admitted.

### 2.2 B14 cache identity

Owner: `owner:b14-cache`.

The registry key has exactly one scope:

- `ARTIFACT cache:`

The private half is generated only to produce a syntactically valid Ed25519 public
identity and is destroyed before activation. B14 does not use it for detached signing.

### 2.3 External BAMF source owner

Owner: `owner:bamf-source`.

Private key: external/off-Studio, with durable primary and recovery custody established
before a bootstrap package can be emitted.

Scopes:

- `ARTIFACT atlas-approval:`
- `ARTIFACT a12-export:`
- `ARTIFACT capability-support:Z.C13_EPISODE`

This owner does not receive `RIGHTS` authority.

### 2.4 External C13 rights owner

Owner: `owner:c13-rights`.

Private key: external/off-Studio, with the same primary-plus-recovery durability rule as
the BAMF source owner. It may be generated in the same operator administration command,
but it is a distinct Ed25519 key and registry owner.

Its sole scope is:

- `RIGHTS c13-source-rights:Z.C13_EPISODE:`

This is intentionally not `rights:`. Generic C09 correction machinery must not turn a
C13 correction credential into authority over B14 rights, unrelated training rows, or
future source families.

## 3. Durable C13 namespace contract

The C13 namespace must be guaranteed where the source identity is authored, not inferred
later by scanning a release during host bootstrap.

### 3.1 Capability/source binding invariant

The admitted C13 release is the only release allowed to bind all four of these values
together:

- capability ID `Z.C13_EPISODE`;
- source anchor `public-formal:bamf.c13.episode-binding/v1`;
- generator `bilqis.c13.episode-binding-generator/v1`;
- oracle `bilqis.c13.episode-binding-checker/v1`.

`factory.curriculum_definition.validate_source_bindings()` is the durable enforcement
boundary. v5 implementation MUST add a source-binding namespace validator that rejects:

- `Z.C13_EPISODE` with any other source anchor/generator/oracle;
- the C13 source anchor/generator/oracle bound to any other capability ID;
- any capability ID beginning `Z.C13_EPISODE` except the exact released capability;
- any future source binding that would make the `capability-support:Z.C13_EPISODE`
  prefix ambiguous.

`source_adapters.c13_episode_release.compile_episode_release()` remains the authoritative
producer of the accepted tuple above. The validation rule is generic release admission
protection; it MUST NOT depend on bootstrap state or a host registry.

### 3.2 C13 correction-rights dependency namespace

Current training provenance emits `RIGHTS rights:<64hex>`, and B14 cache identity deliberately
parses that exact shape. v5 therefore **does not replace, alias, or broaden** the existing
generic rights dependency. It remains part of causal/cache identity exactly as implemented.

Instead, the retained C13 capability-support artifact receives one additional correction-only
dependency:

`RIGHTS c13-source-rights:Z.C13_EPISODE:<digest>`

where `<digest>` is the one unique 64-hex suffix from the support artifact's already-proven
generic `RIGHTS rights:<digest>` dependencies. Zero generic rights digests, more than one unique
digest, or a malformed digest fails support materialization for the reserved C13 capability.

The implementation seam is
`bilqis_mlx/runtime/_correction/owners/capability_support_materialization.py::materialized_support`.
After `_verify_anchor_proofs()` has established the accepted source anchors, the existing
generic dependencies are built unchanged. Only when `capability_id == "Z.C13_EPISODE"`, the
materializer extracts the unique generic rights digest and adds the correction-only dependency.
Callers and row payloads cannot supply its namespace. The C13 mapping is literal:

- capability: `Z.C13_EPISODE`
- source family: `bamf.c13.episode-binding/v1`
- correction-rights prefix: `c13-source-rights:Z.C13_EPISODE:`

Any partial capability match is invalid. The correction canary and future #529 C13 correction
proof use the new disjoint dependency. Because it does not begin `rights:`, the B14 cache bridge
continues to observe exactly one generic `rights:<64hex>` value and its identity contract is
unchanged.

### 3.3 Capability-support revalidation namespace

The only external source-owner ARTIFACT revalidation namespace admitted at bootstrap is
`capability-support:Z.C13_EPISODE`.

The source-binding invariant above is the authoritative reason this prefix is safe. Host
bootstrap validates the checked-in manifest and canary against that rule; it does not
perform a best-effort census of whatever capabilities happen to exist on one machine.

## 4. Long-lived key custody and bootstrap packages

### 4.1 Operator key records

Three long-lived private-key records exist outside Git before Studio activation:

- BAMF source-owner record, schema `bilqis.mlx.external-source-owner-key/v1`, owner
  `owner:bamf-source`;
- C13 rights-owner record, same schema, owner `owner:c13-rights`.
- C06 signer record, schema `bilqis.mlx.source-authority-signer/v1`, owner
  `owner:c06`.

Canonical fields are exactly:

```json
{
  "schema": "bilqis.mlx.external-source-owner-key/v1",
  "owner_id": "owner:...",
  "private_key_hex": "<64 lowercase hex>"
}
```

The C06 record reuses the already-implemented fixed-host signer schema exactly:

```json
{
  "schema": "bilqis.mlx.source-authority-signer/v1",
  "owner_id": "owner:c06",
  "private_key_hex": "<64 lowercase hex>"
}
```

Each key record is secret and MUST never be written to stdout, Git, an issue, a Drive
receipt, the public bootstrap package, or the Studio registry. The C06 signer is the only
one of these private records ever installed on the Studio.

### 4.2 Mechanical recovery precondition

For each long-lived private record, initialization requires a primary path and a recovery
path on a different physical Darwin whole disk. The tool resolves each parent with
`/usr/sbin/diskutil info -plist`, requires a non-empty `ParentWholeDisk`, and requires the
primary and recovery `ParentWholeDisk` values to differ. It also requires their `st_dev`
values to differ. Two APFS volumes or partitions on the same parent disk therefore do not
qualify. A normal protected off-machine backup may add stronger durability but is not
substituted for this mechanically checked second storage failure domain.

Before any public package is emitted, the tool MUST:

1. create both files through same-directory temporary files;
2. set mode `0600` before secret bytes are written;
3. fsync the file contents;
4. rename atomically to the requested final name;
5. fsync each containing directory;
6. require primary and recovery parents to resolve to different `st_dev` and
   `ParentWholeDisk` values;
7. reopen both files and require byte-for-byte identity;
8. derive the public key from each copy and require the same expected owner/public identity.

The public bootstrap package command refuses to operate if any recovery copy is absent,
same-filesystem/whole-disk, different, unreadable, or derives a different key. This makes exact C06,
BAMF-source, and C13-rights recovery durability a mechanical activation prerequisite.

The C06 primary record is also the secret transfer artifact. Its exact SHA-256 is carried as
a public digest in the bootstrap package and supplied separately to `host-install`; the
private record itself is never embedded in the public package.

### 4.3 Public bootstrap package

The operator emits one public package, schema
`bilqis.mlx.c09-host-bootstrap-package/v1`. It contains no private key material.

Required top-level fields are exactly:

```text
schema
authority_manifest_sha256
source_revision
c06_public
source_owner_public
c13_rights_owner_public
b14_cache_public
c06_signer_record_sha256
canary_bundle_sha256
```

Each `*_public` object contains exactly `owner_id` and `public_key_hex`.
`authority_manifest_sha256` binds the exact canonical bytes of
`authority-manifest-v2.json`.

The B14 keypair is created during the first successful operator initialization. Only its
public identity is retained. Because the private half is intentionally destroyed, the public
bootstrap package is itself required recovery evidence for B14 identity and MUST be written
to both a primary and recovery path on different `st_dev` and `ParentWholeDisk` values before
the command succeeds.
An exact rerun reconstructs the package from the three retained private-key public identities
and the previously stored B14 public identity; it never silently invents a replacement B14 key.

The package is written canonically to both durable package paths and its SHA-256 is printed
as the public trust-transfer value needed by the host administrator. The package file is
public but security-sensitive:
its digest selects the immutable trust identities that will enter a newborn lineage.

### 4.4 Complete typed canaries

Signed canaries are **not** carried in the public package. A valid C07 approval or A12 export
clearance is an authorization artifact even when created for bootstrap, so operator
initialization writes a separate mode-`0600` protected bundle with schema
`bilqis.mlx.c09-host-bootstrap-canaries/v1`. The public package commits only its SHA-256.
Canary signatures are deterministic Ed25519 signatures over the frozen templates, so the
protected bundle can be regenerated exactly from retained long-lived private keys and does not
need its own recovery copy. It MUST NOT be committed, logged, posted, or retained on the Studio
after successful bootstrap verification.

The BAMF source-owner canaries are:

1. one complete `AtlasSourceApproval`, including all current fields required by C07 v2;
2. one complete A12 export-clearance vector containing:
   - `ExportClearanceReceipt`;
   - the exact `AtlasArtifactSelection` required by
     `validate_export_clearance_context()`;
   - one exact `SourceFrontier` whose rights epoch/correction generation and grants match
     the receipt;
   - the exact exported artifact digest tuple;
   - the registered source pin data required by `_require_registered_source_pin()`;
3. one signed `RevalidatedArtifact` whose artifact ID is exactly
   `capability-support:Z.C13_EPISODE`, plus the unsigned expected fields of the
   `StateTransition` that `revalidate_node()` must derive locally from it.

The C13 rights-owner canary is one `CorrectionEvent` whose dependency is exactly
`RIGHTS c13-source-rights:Z.C13_EPISODE:<fixed-bootstrap-digest>`.

Every canary contains its `source_owner`; the package also carries the corresponding
public-key object explicitly. Host validation MUST verify the protected bundle digest against
`canary_bundle_sha256`, then verify each canary through the real domain validator and the
pending registry, not merely verify raw Ed25519 signatures.

The A12 canary is pinned to the one repository-owned A01 source entry currently accepted by
`bilqis_mlx/semantics/atlas_source_pins_v1.json` and its frozen registry digest
`842b66ad7b19ddb333610668410820b3f5d703fa1e452d014755c2c5cc308cee`:

- bundle ID `5f8fba20ecc0adebf39c3b663fdffa4f766e780915197f09d116713042a479e7`;
- semantic release `58e0c281b5da18b9b7e6c803709b29eeeb0a88f16b06f48de692808e2fb88306`;
- source bundle ID `f1c89c1d1bcd72695c81f8e777d0fbbdf446e92cb27132bebf1cd6873ec689ec`;
- selection path `bootstrap-canary-a01` (the path is non-authoritative; the three pinned
  identities are what `_require_registered_source_pin()` verifies);
- `SourceFrontier(rights_epoch=0, correction_generation=0, grants=())`;
- exported artifact digests `("1" * 64, "2" * 64)`;
- private artifact digests `("3" * 64,)`;
- revoked artifact digests `("4" * 64,)`;
- revocation lineage `("5" * 64,)`.

The receipt's `source_frontier_sha256` is derived from that exact literal frontier with the
existing `contract_digest()` function. If the checked-in source-pin registry digest or its
sole accepted entry changes before v5 implementation, the design is stale and returns to EGM;
the bootstrap tool MUST NOT silently select a different live pin.

All remaining unsigned canary fields are frozen under `canary_templates` in
`bootstrap-contract-v1.json`; signatures are the only values created at operator initialization.
The C13 support canary deliberately exercises the **unchanged** revalidation branch: identical
old/new content, `eligible=true`, and `changed=false`. Its purpose is to prove that
`owner:bamf-source` can sign the exact `capability-support:Z.C13_EPISODE` artifact namespace
and that the runtime derives the expected transition and clears an unchanged hold. The
external owner does not issue or sign the `StateTransition`. This canary does not claim to
execute the separate changed-support branch that schedules fresh source requalification.

## 5. Exact CLI contract

The administration entry point is:

`python3 scripts/operations/bamf_source_authority_bootstrap.py ...`

It exposes exactly these subcommands.

### 5.1 `operator-init`

```text
operator-init
  --c06-primary <absolute-non-repo-path>
  --c06-recovery <absolute-non-repo-path-on-different-filesystem>
  --source-owner-primary <absolute-non-repo-path>
  --source-owner-recovery <absolute-non-repo-path-on-different-filesystem>
  --c13-rights-primary <absolute-non-repo-path>
  --c13-rights-recovery <absolute-non-repo-path-on-different-filesystem>
  --package-primary <absolute-non-repo-path>
  --package-recovery <absolute-non-repo-path-on-different-filesystem>
  --canary-out <absolute-protected-non-repo-path>
```

Behavior: create-or-verify the C06, BAMF-source, and C13-rights private keys and their
independent-storage recovery copies; create B14 identity once; emit/verify both canonical
public-package copies; emit the protected canary bundle; and print only package/canary paths,
their SHA-256 digests, C06 secret-record SHA-256, owner IDs, and public keys. Exact rerun is
idempotent. Any missing recovery artifact,
same-filesystem/whole-disk recovery, conflicting key, or conflicting B14 public identity fails closed.

### 5.2 `operator-verify`

Same nine path arguments as `operator-init`.

Behavior: mutation-free verification that all private primary/recovery pairs and both public
package copies match and that the public package can be reconstructed byte-for-byte with the
same digest. It also reconstructs the protected canary bundle byte-for-byte and requires the
same digest committed by the public package.

### 5.3 `host-install`

```text
host-install
  --runtime-user <local-account-name>
  --package <absolute-path>
  --package-sha256 <64-lowercase-hex>
  --canary-bundle <absolute-protected-path>
  --c06-signer <absolute-protected-path>
  --c06-signer-sha256 <64-lowercase-hex>
  --receipt-out <absolute-non-repo-path>
```

Requirements: Darwin and EUID 0. The command accepts the protected C06 signer record only as
the explicitly authenticated secret input above. It does not accept registry bytes, arbitrary
signer JSON, owner IDs, scopes, destination paths, or an authority manifest from the caller.
The signer record must be canonical `bilqis.mlx.source-authority-signer/v1` bytes for
`owner:c06`; its digest must match both `--c06-signer-sha256` and the digest committed by the
public package, and its derived public key must match `c06_public` before it is staged.

### 5.4 `host-verify`

Same seven arguments as `host-install`.

Behavior: no key generation and no trust-root mutation. Verify package digest, fixed host
files, runtime-UID signer proof, exact registry composition, and receipt reproducibility.

## 6. Protected host package staging

`host-install` does not parse the caller-owned package in place after privilege elevation.
It performs this sequence before private-signer staging or trust-root activation:

1. open the supplied package `O_RDONLY|O_NOFOLLOW`;
2. require a regular file and a size limit;
3. hash the exact bytes and compare with `--package-sha256`;
4. parse and require canonical package bytes;
5. verify `authority_manifest_sha256` against the checked-in v2 manifest;
6. authenticate the protected canary bundle with `O_RDONLY|O_NOFOLLOW`, exact mode `0600`,
   regular-file, canonical-schema, and exact SHA-256 matching `canary_bundle_sha256` from the
   authenticated public package;
7. authenticate the protected C06 signer input with `O_RDONLY|O_NOFOLLOW`, regular-file,
   safe-owner/mode, canonical-schema, exact SHA-256, and derived-public-key checks;
8. create the root-owned bootstrap directory if absent;
9. copy the exact package bytes to fixed pending name
   `/private/etc/entif-ai/bilqis/.source-authority-bootstrap-package.pending`;
10. copy the exact canary bytes to fixed pending name
    `/private/etc/entif-ai/bilqis/.source-authority-canaries.pending`, mode `0600`, UID 0;
11. fsync both staged files and fsync the containing
   directory;
12. reopen both staged files through the root-owned directory descriptor and require the same
    digests before any private signer is staged or any trust-root activation step begins.

The staged package is never a runtime trust root. It is an authenticated bootstrap input.
After successful activation it may be retained as public recovery evidence or removed only
after the receipt exists and the directory has been fsynced.
The protected canary pending file MUST be unlinked and the `bilqis` directory fsynced after
all pending-registry canary validation and the pre-activation runtime-UID signer smoke pass,
but before the final registry activation publish. It can be re-staged from the authenticated
operator input after an interrupted pre-activation attempt.

## 7. Darwin host-state contract

Fixed logical paths remain:

- `/etc/entif-ai/bilqis/source-authority-registry.json`
- `/etc/entif-ai/bilqis/source-authority-signer.json`

Physical Darwin paths are under `/private/etc/entif-ai/bilqis/`.

### 7.1 Directory state

The installer creates/verifies the `entif-ai` and `bilqis` directories as UID 0-owned,
non-group/world-writable directories and opens all descendants fd-relative with
`O_NOFOLLOW`. Creation or metadata changes are followed by an fsync of the containing parent
directory before child state may be treated as durable.

### 7.2 Public registry

Final registry mode is `0444`, UID 0, with no non-root mutating ACL. It must satisfy the
existing #950 production fixed-path reader unchanged.

### 7.3 C06 signer ACL

Final signer mode is `0400`, UID 0. The only non-root `ALLOW` ACL entry is the configured
runtime UID and it MUST contain `ACL_READ_DATA`. It MUST contain none of:

`ACL_WRITE_DATA`, `ACL_APPEND_DATA`, `ACL_DELETE`, `ACL_DELETE_CHILD`,
`ACL_WRITE_ATTRIBUTES`, `ACL_WRITE_EXTATTRIBUTES`, `ACL_WRITE_SECURITY`,
`ACL_CHANGE_OWNER`.

No group `ALLOW` ACL is permitted. Any additional non-root `ALLOW` principal rejects the
signer. The signer reader must inspect and enforce `ACL_READ_DATA`; successful `open()` is not
used as a substitute for ACL verification.

Darwin permission decoding is amended deliberately rather than by adding `ACL_READ_DATA` to
the current mutation map. `_darwin_source_authority` MUST decode `ACL_READ_DATA = 1 << 1`
alongside the existing rights, while `_MUTATION_PERMISSIONS` remains an explicit frozen set of
only the eight mutation names listed above. The administration tool installs the single read
ACE on the already-open signer descriptor with libSystem's descriptor APIs
`acl_init` -> `acl_create_entry` -> `acl_set_tag_type(ACL_EXTENDED_ALLOW)` ->
`mbr_uid_to_uuid(runtime_uid)` -> `acl_set_qualifier` -> `acl_get_permset` ->
`acl_add_perm(ACL_READ_DATA)` -> `acl_set_fd_np(fd, acl, ACL_TYPE_EXTENDED)`, then frees the
ACL and immediately re-reads it with the existing `read_extended_acl(fd)` path. Any API
failure or any readback difference fails closed. No path-based ACL mutation command is used.

### 7.4 Runtime-UID child smoke

Root-only readback is insufficient. After final activation, `host-install` forks a child,
clears supplementary groups, adopts the configured runtime primary GID and UID, then uses the
production fixed registry reader and production fixed signer reader. The child performs one
bounded C06 signature over a bootstrap-only `salience-policy:bootstrap-smoke` dependency and
verifies it through the installed registry. The child returns only pass/fail and public
identity/digest data through a pipe. It never returns the private key.

Failure of the runtime-UID child smoke makes installation incomplete and MUST be reported as
an activation failure. Because the registry is already immutable once activated, this state is
not repaired by generating new keys; recovery restores exact state or stops.

## 8. Crash-safe host activation state machine

Fixed pending names:

- `.source-authority-bootstrap-package.pending`
- `.source-authority-canaries.pending`
- `.source-authority-signer.pending`
- `.source-authority-registry.pending`

Before either final authority file exists, pending files are unactivated scratch and may be
recreated only by root after exact-state validation.

The first-install sequence is:

1. authenticate and durably stage the public package;
2. resolve the runtime account to stable UID/GID;
3. authenticate the protected C06 signer record and derive its public key;
4. construct the exact four-owner registry from code constants plus the package public keys;
5. write pending signer and pending registry using same-directory temporary files;
6. fsync file contents, apply UID/mode/ACL metadata, reopen and validate metadata/content;
7. fsync the `bilqis` directory after both pending names and their final metadata are visible;
8. validate C06 against the pending registry, B14 selector semantics, and every complete typed
   external canary against the pending registry;
9. publish pending signer to `source-authority-signer.json` with Darwin
   `renameatx_np(..., RENAME_EXCL)`; an existing final name is never overwritten;
10. fsync the `bilqis` directory;
11. while the registry is still absent, fork the configured runtime UID/GID child and use the
    production fixed signer reader against the already-constructed pending registry object;
    require the bounded C06 bootstrap signature to verify before activation;
12. unlink the protected pending canary bundle and fsync the `bilqis` directory;
13. publish pending registry to `source-authority-registry.json` **last** with Darwin
    `renameatx_np(..., RENAME_EXCL)`; an existing final name is never overwritten;
14. fsync the `bilqis` directory; this fsync completes the one-way activation;
15. reread the registry through the production fixed-path reader;
16. perform the runtime-UID child smoke again through both production fixed readers;
17. write the public host receipt atomically and fsync its containing directory.

The final registry publish is forbidden unless steps 1-12 have completed and every pending
file plus directory entry required for recovery has been fsynced.

### 8.1 Recovery matrix

- no final files: exact complete pending state may resume; incomplete pending state may be
  discarded and recreated after validation;
- final signer, no final registry: resume only from the exact pending registry that binds the
  final signer's public key and both authenticated external public keys; if the exact pending
  registry is absent, the state is invalid because the required pre-publish directory fsync
  contract was violated;
- final registry present: verify-only. The exact final signer must already exist. No key,
  owner, scope, ACL, or registry mutation is allowed;
- any conflicting final file: fail as rotation/migration, never repair in place.

No post-generation backup step is required on the Studio because activation cannot begin until
operator verification has already proved byte-identical C06 primary and recovery records on
different filesystems. The host receipt binds the exact imported C06 record digest. Recovery
of another trusted Studio imports those exact old bytes; it never generates a replacement key.

## 9. Host receipt schema

Public receipt schema: `bilqis.mlx.c09-host-bootstrap-receipt/v1`.

Required fields:

```text
schema
source_revision
authority_manifest_sha256
bootstrap_package_sha256
canary_bundle_sha256
registry_record
registry_semantic_digest
registry_file_sha256
owners
runtime_user
runtime_uid
runtime_gid
registry_path
signer_path
registry_stat
signer_stat
signer_acl_summary
signer_record_sha256
runtime_uid_smoke

```

`registry_semantic_digest` is `SourceAuthorityRegistry.digest`; `registry_file_sha256` is the
SHA-256 of the exact canonical installed registry bytes. They MUST NOT be conflated.
`owners` contains only owner IDs, public keys, and scopes. `runtime_uid_smoke` contains only
the child EUID, public signer identity, dependency key, signature verification result, and
registry digest. No private key or reversible secret appears in the receipt.
